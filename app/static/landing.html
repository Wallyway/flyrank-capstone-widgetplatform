How it works

Three request paths,
three sets of rules.

The owner's API is authenticated and tenant-isolated. Delivery is public and cached like a CDN. The submission endpoint is public, hostile-by-default, and never trusts a single field it is given.

1

Create a widget

An authenticated CRUD API, isolated per tenant in SQL. Another customer's widget answers 404, never 403 — a 403 would confirm the id exists.

2

Paste one line

A short-lived loader pulls a versioned bundle cached for a year and a config cached for a minute. The widget renders inside a shadow root, so the host page cannot restyle it.

3

Catch what comes back

Size limit, field validation, rate limits per IP and per widget, a honeypot, an idempotency key, geo enrichment that degrades instead of failing, and a notification that runs off the request path.

The embed

This is the whole integration.

Everything the widget needs — its config, its rendering, its submission wiring — flows from this one tag.

Paste into any page <script src="http://localhost:8000/widget.js?id=wgt_demo_signup" async></script>

The widget on the right is real: it is being served by this API and it posts to /public/submissions like any other visitor. It is same-origin here, though — the cross-origin proof lives on the test site, which nginx serves from a different port and which deliberately tries to repaint the widget with hostile CSS.

Under it

Built to fail politely.

Two dependencies are allowed to break, and each breaks differently on purpose.

Enrichment degrades

IP to location runs inline with a hard timeout and a provider chain. Provider A down, provider B answers. Both down, the submission is stored without geo. It can make a lead poorer; it can never make one fail.

Notifications defer

The request writes a job in the same transaction as the submission and returns. A worker retries on a growing backoff and dead-letters with an alert. A dead SMTP host cannot even slow a submission down.

Retries land once

An Idempotency-Key plus a partial unique index. Two identical requests arriving together still produce exactly one row, which a check-then-insert would not.
